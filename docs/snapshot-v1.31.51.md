## 本轮一句话

一部《山海经》的里程，一直躺在数据里没人读——**276 段、75,589 里**。这一版把它读出来，
做成舆地页的第二视图「山海道里图」。**一期只做「看」，不改玩法。**

## 需求与结论的偏差（最重要的一条）

用户的设想是「canvas 绘制的五座山系地图，自由探索，跨系要慢慢走过去」。

做了**三版二维地图原型，全部失真**。不是算法问题，是数据性质问题：

| 事实 | 后果 |
|---|---|
| 原文里程是**路径长度**，不是坐标 | 北山经诸段全是「北」→ 是竖线；南山经全是「东」→ 是横线。各系接不上 |
| **五系之间原文不载相通里程** | 每经从自己的首山起算。「跨山系多远」在文本里不存在 |
| 26 条经形状差异极大 | 北次三经 3,947×7,270 的竖条 vs 南次一经 2,700×0 的横线，塞进等高行必然压扁 |

于是改用**道里图**：一条经一行，横轴就是真实里程，全图同一比例尺。

| 项 | 值 |

## 三处必须诚实的地方

| 问题 | 做法 |
|---|---|
| 各经长度悬殊 | **全图同一比例尺**。各自归一化会把 12,040 里画得和 2,700 里一样长——那是撒谎 |
| 中山经九经未载分段里程 | 按山序等距排布 + **虚线** + 行末「未载里程」，不用正弦曲线冒充地形 |
| 五系之间不载相通里程 | `roadBetween` 跨系返回 **null**，不臆造 |

## 新增判据（引擎层）

| 函数 | 管什么 |
|---|---|
| `regionLegs(region)` | 统一两种 `legs` 格式：对象式（`legs.路线`，用 id）/ 数组式（`legs[]`，用 `from`/`to` 山名） |
| `regionRoad(regionId)` | 一条经的行程表：每座山的累计里程、等级、是否有真实里程 |
| `regionRoadLength(regionId)` | 一条经的里程合计 |
| `roadBetween(fromId, toId)` | 两山路程；**跨经 / 跨系返回 null** |

## 四条规律（写进 ROADMAP）

1. **先问数据支不支持这个形态，再决定做不做**——「用户想要地图」不等于「能做地图」。
2. **归一化会撒谎**——各自归一化会把长短差异抹平，短本身也是信息。
3. **缺数据要标出来，不要填得好看**——正弦曲线填满很像地形，但那是假的。
   测试里直接钉死「不许用 `Math.sin`」。
4. **等比缩放的代价要单独处理**——不是「让玩家横滑」（会丢失左端经名），而是给两档版式。

## 关于「行进成本」（二期）

一期**没有路程成本**，点击仍瞬移。不做进成本的三条理由：

1. 违反放置契约——离线时「还在路上」是纯挫败；
2. 时间尺度失控——跨五系 75,589 里按 5 里/秒是 **4.2 小时**，等于 4,300 次采集的时间；
3. 与 v1.31.47~50 三轮「让前往更顺手」的方向相反。

若要做，正确形态是「行进＝另一种行动」：路上有沿途产出、离线照走、到站自动接原动作。
**判据已在位**（`roadBetween` 同经可算、跨系 null），二期只需定两个参数：
「一里等于几秒」与「跨系距离怎么定」。
