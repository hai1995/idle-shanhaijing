## 本轮一句话

前两轮收了采集（v1.31.48）与图鉴（v1.31.49），**舆地层还停在旧口径上**——它有三处只认主产地，于是同一个问题在三个地方同时发作。

## 三个 bug

| bug | 现象 | 根因 |
|---|---|---|
| **进度条分母算少** | 238 座山的「已著录 x/y」偏小；**136 座分母为 0，进度条压根不出现** | `nodeRecordProgress` 只按 `it.node`（主产地）统计 |
| **材料来源指错山** | **18 处**指向锁着的山，而同一材料在别的山早就能采 | `materialNodesForSkill` 每种材料只取 `it.node` |
| **产出地只给一座** | 「金」产于 42 座山，技能卡却只写「招摇之山」 | `nodeForSkill` 取池里第一件物的**主产地** |

### 样本一：柢山的进度条

雄黄的主产地是西山十六（需舆地 41 级），但它在柢山（3 级）就能采。
旧口径下柢山的分母 = **0** → 舆地上写「0/0」，进度条不出现。
玩家在柢山采到雄黄，舆地上柢山仍然什么都不显示。

新口径：**录 0/2**（雄黄 + 另一件次产地物）。

### 样本二：琢玉的材料来源

「美玉」此前写西山十四（需 37 级），可它在西山二号（31 级）早就能采。
玩家按着做，一路的山都锁着。

## 新增判据（引擎层，与采集、图鉴两层同源）

| 函数 | 管什么 |
|---|---|
| `nodeSourceItems(itemId)` | 一件物的**产地候选集**：`nodes[]` 全集 + 主产地（`nodes[]` 里常常不含 `node`，两个都要） |
| `nodeHasItem(nodeId)` | 一座山的著录分母与已著录数 |
| `skillSourceNodes(skillId)` | 一门技艺的全部产地候选 |
| `materialSourceNodes(itemId)` | 一件材料的产地候选（与 `nodeSourceItems` 同一口径） |
| `pickReachableNode(cands)` | **共用**：在候选集里挑一处现在能去的（已解锁优先，其次门槛最低） |

`codexReachableNode` 此前自己写了一遍「已解锁优先、其次门槛最低」，
本轮改为复用 `pickReachableNode`——抽出来不换用等于多一个函数。

## 四条规律（写进 ROADMAP）

1. **判据统一不是一次收完的，是要反复往下捋**——采集 → 图鉴 → 舆地，三轮才收干净。
   第一轮就该做全库 `grep` 旧写法，而不是等下一轮被玩家撞见。
2. **进度条的分母也是判据**——「x/y」里的 y 更容易被漏掉，因为 x 看起来「差不多对」。
3. **清单项要能按它指路**——清单的用途是照着走，就必须优先给「现在能去的那处」。
4. **共用判据要真的共用**——抽出来不换用，等于多了一个函数。
