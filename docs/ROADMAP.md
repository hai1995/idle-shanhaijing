## 二之二、这一轮补上的交互一致性（v1.31.47）

同一个动作在不同页面有两套规矩，是这类游戏最容易长毛的地方。本轮把三处对齐了：

| 动作 | 此前 | 现在 |
|---|---|---|
| 图鉴 → 舆地 | 异兽 / 物品能指路，山川不能（447 条） | 一律能指；锁着的山写明需 N 级 |
| 再来一轮 | 征伐页有「再战」，舆地页没有 | 舆地页有「再采」，沿用上次的物与次数；正在采同一件时不显示（顶栏已写「余 N 次」） |
| 在线 vs 离线 | 统计页只有在线速率 | 近况面板补一行离线一小时折算，并给百分比对照 |

**规律**：凡有「上一次做了什么」的地方，都该能一键再来一次（`Prefs.last*`）；
凡是能算出一个数的地方，都该给一个参照物（在线速率 ↔ 离线折算、当前 ↔ 累计均值）。


## 二之三、判据单一来源：采集这一轮（v1.31.48）

采集是最基础的动作，可判定「能不能采」的规则却散在五处：引擎 `doGather`、手动采集
`startActivity`、队列采集 `startEntryActivity`、舆地按钮渲染、离线结算。各写各的，
于是同一件事有了五个口径——本轮修的三个 bug 全是口径打架打出来的：

| bug | 现象 | 根因 |
|---|---|---|
| 越级采不到 | 舆地标「越级 84% 可采」，点下去被弹回 | 引擎允许越 8 级硬采，开始动作却是一道硬门槛 |
| 多产地被拽走 | 站在次产地采东西，被传送回主产地 | 只认 `it.node`，不认 `nodes[]` 全集 |
| 万物山采不到 | 积石之山「万物无不有焉」，一件也列不出 | 引擎放行任何物，UI 按 `nodes[]` 过滤 |

**收拢后的判据分层**（判据与「能否前往」严格分开）：

| 层 | 函数 | 口径 |
|---|---|---|
| 是不是采集之物 | `isGatherSkill` / `GATHER_SKILLS` | 白名单四门；异兽的 `lie`/`puyi` 不在其列 |
| 能不能采（等级） | `gatherAllowed` | 不越级满效；越级 ≤8 级衰减；>8 级拒 |
| 此地产不产 | `gatherAllowedAt` | 产地清单命中 / 万物山通吃 / 主产地兜底 |
| 产地在哪 | `gatherSources` / `gatherHomeNode` | `nodes[]` 全集；`node` 仅主产地 |
| 去哪采 | `gatherReachableNode` | 全部产地里挑一处**已解锁**的 |

**规律**：解锁属于「能否前往」，不属于「是否产地」。把两件事混在一处，
会让引擎每帧调用的离线结算被「当前站在哪」搅乱（v1.31.48 曾因此回归三处）。
判据分层时，先问「这件事的答案会不会随时间/位置变化」——会变的（如解锁、当前山）
不该进判据，该进调用层。

## 二之四、判据统一要「收干净」（v1.31.49）

上一轮把采集的判据收成单一来源，收尾时留了个尾巴：图鉴仍只认主产地。
结果是同一件事在两个页面上给出两个答案——采集页说「这座山能采」，
图鉴说「需 41 级」。**46 件物被指向了去不了的远山**。

**规律一：判据统一要连着上下游一起收**

「同一件事只留一处定义」听着简单，实际上要问：**这件事在哪些地方被判断过？**
采集这件事被判断了五处（引擎 / 手动 / 队列 / UI / 离线），图鉴这件事被判断了三处
（`codexNode` / `codexWhereOf` / `codexGoBtn`）。只收一处、其余照旧，
就会造出「新的单一来源 vs 旧的局部口径」——比统一前更糟，因为两处都自称权威。
收尾时应当顺着**调用链**往下捋一遍，而不是只看自己改的那一层。

**规律二：清单里全是不可执行的条目，就等于没有清单**

图鉴「仅未录」此前是一张 447 张卡的清单，其中 445 张锁着。上一轮以为这是视觉问题
（虚线签太吵），降噪即可；实际它是**功能问题**：一张全是锁的清单回答不了
「我现在该做什么」。加一枚「可往 N」筛选后，开局 447 张收敛到 2 张。

**规律三：降噪与增信是一回事**

「需 41 级」这个虚线签，噪音来自**边框**（445 个框），
信息价值来自**数字**（要练到几级）。去掉边框、留下数字，并把它换成
所有候选产地里的**最低**门槛——同一行字，从「劝退」变成「指路」。

## 二之五、判据统一要「顺着调用链往下捋」（v1.31.50）

上一轮把图鉴接上了引擎，收尾时只改了图鉴那一层。**舆地层还停在旧口径上**，
而且它有三处只认 `it.node`——于是同一个问题在三个地方同时发作。

**规律一：判据统一不是一次收完的，是要反复往下捋**

采集（v1.31.48）→ 图鉴（v1.31.49）→ 舆地（v1.31.50），三轮才把一个概念收干净。
每轮都只改了自己直接动过的那一层，于是每轮都能再挖出两处旧口径。
**教训**：判据统一的第一轮就该做一次全库扫描（`grep` 同一个旧写法），
而不是等下一轮被玩家撞见。

**规律二：进度条的分母也是判据**

舆地「已著录 x/y」的分母按主产地算，238 座山偏小、136 座分母为 0
（进度条压根不出现）。玩家在柢山采到雄黄，舆地上柢山还是「0/0」。
**凡是「x/y」这种成对的数字，y（分母）也是判据**——它比 x 更容易被漏掉，
因为 x 看起来「差不多对」。

**规律三：清单项要能按它指路**

「材料来源」此前 18 处指向锁着的山，而同一材料在别的山早就能采。
清单的用途是**照着走**，所以清单项必须优先给「现在能去的那处」，
而不是数据里排序最靠前的那处。已解锁的排前面，是这类清单的通用规矩。

**规律四：共用判据要真的共用**

本轮把「在候选集里挑一处现在能去的」抽成 `pickReachableNode`，
图鉴那处原本自己写了一遍——收尾时改成复用。抽出来不换用，等于多了一个函数。

## 二之六、地图：先问数据支不支持这个形态（v1.31.51）

用户提的玩法是「canvas 绘制的五座山系地图，自由探索，跨系要慢慢走过去」。
做了三版二维地图原型，**全部失真**——不是算法问题，是数据性质问题：

- 原文里程是**路径长度**，不是坐标。北山经全是「北」，所以是竖线；南山经全是「东」，是横线。
- **五系之间原文不载相通里程**，每经从自己的首山起算。用户想要的「跨系穿梭」
  恰好是文本里不存在的那部分。
- 26 条经形状差异极大（3,947×7,270 的竖条 vs 2,700×0 的横线），塞进等高行必然压扁。

**规律一：先问数据支不支持这个形态，再决定做不做**

「用户想要地图」不等于「能做地图」。数据只支持「一维里程」，硬做二维就是编。
落地方案是**道里图**（一维里程轴 + 分系分行），它诚实地回答了「哪条经多长、
走到几成」，而二维地图只能靠编造坐标来回答「在哪」。

**规律二：归一化会撒谎**

第一版原型给每条经单独归一化到自己的格子，结果 2,700 里的南次一经和 12,040 里的
北次三经一样长。**全图同一比例尺**才是诚实的——代价是短经几乎看不见，
但「短」本身就是信息。

**规律三：缺数据要标出来，不要填得好看**

中山经九经原文未载分段里程。用正弦曲线填满很好「看」，但那是假的。
最终按山序等距排布 + 虚线 + 行末「未载里程」，并在测试里钉死「不许用 Math.sin」。

**规律四：等比缩放的代价要单独处理**

SVG 按容器缩放很省事，但 447 座山挤进 430px 屏，字只有 4px。
解法不是「让玩家横滑」（会丢失左端经名），而是给两档版式：
全图用宽画布（820）看形态，单系用窄画布（430）看细节。

**关于「行进成本」（用户的初始设想）**

一期只做「看」，**没有路程成本**，点击仍瞬移。原因是三条：

1. 违反放置契约——离线时「还在路上」是纯挫败；
2. 时间尺度失控——跨五系 75,589 里按 5 里/秒是 4.2 小时，等于 4,300 次采集的时间；
3. 与 v1.31.47~50 三轮「让前往更顺手」的方向相反。

若要做，正确形态是「行进＝另一种行动」：路上有沿途产出、离线照走、
到站自动接原动作。**判据已经在位**：`roadBetween` 同经可算、跨系返回 null，
二期只需定「一里等于几秒」与「跨系距离怎么定」两个参数。

## 五、技术债

- ~~`src/ui.js` 单文件 4500 行~~（已拆，v1.31.8）：按页分成 `src/ui/` 下 7 个文件，
  `core.js`（1300 行）持有 `UI` 对象并最先加载，其余按页顺序。加载顺序仍只由 `index.html` 决定；
  构建脚本与测试都是从 `index.html` / 文件清单读，没写死数量。**再加页面时**：
  新建 `ui/xxx.js` → 在 `index.html` 里排在 `misc.js` 之前 → 测试的 `UI_FILES` 同步加一项。
- 全部渲染走 `innerHTML` 重建；页面级状态（展开态、输入框）需手动保存在 `UI` 上。长期可考虑用极小的响应式层替换。
  **输入框是这条路线最先咬人的地方**（v1.31.46）：整页重建会顺手销毁正在组合的输入法状态，
  中文拼音因此输不进去。规律已经摸清——**凡是有输入框的地方，输入时只走局部刷新，不重建节点**：
  配方检索（`patchRecipeList`）、图鉴检索（`patchCodexList`）都已照此办理，新增输入框时请沿用。
- 行内事件属性对「组合事件」不可靠：`oncompositionstart` / `oncompositionend` 需要有
  `oncompositionstart` 这个 IDL 属性才生效，而它并非所有内核都实现（headless Chromium 里
  `'oncompositionstart' in window` 就是 false）。凡是要接 `composition*`，一律用
  `addEventListener` 绑（见 `bindCodexSearch`）。
- `test/engine.test.js` 单文件 5200 行、89 节；按模块拆文件时注意 `vm` 上下文是共享的，`section` 顺序即状态顺序。
